# 项目改造计划

## 目的

准备基于这个项目 https://github.com/chatboxai/chatbox 进行改造，添加一些额外的功能。

为了方便继续合并上游代码，尽量会以独立的方式新增功能，以最少的代码进行改造。

尽量实现 Windows+Android 两端就行了，如果不复杂的话，其他端也同步实现，具体看功能。

## 需求

### 1.新增第三方API生图

目前官方只支持他自己的生图，不支持第三方，需要参考对话模式那样能选到自行配置的生图API。

#### 分析结论（2026-11-02）

经代码核查，**该需求在当前 fork（chatboxai/chatbox CE）中已完整实现，无需改动代码**：

- **左侧导航入口**：`src/renderer/Sidebar.tsx:115` 已有跳转 `/image-creator` 的按钮。
- **图片生成页面**：`src/renderer/routes/image-creator/index.tsx`，输入框下方左侧即模型下拉框 `ImageModelSelect`。
- **下拉框已支持的第三方 provider**（`useImageModelGroups` → `buildImageModelGroups`，见 `packages/chatbox-core/src/application/image-generation/catalog.ts`）：
  - ChatboxAI（官方）
  - OpenAI（非 OAuth 鉴权时）
  - OpenRouter
  - Gemini（内置 + 自定义 Gemini provider）
  - **自定义 OpenAI 兼容 provider**（`catalog.ts:142-150`，匹配 `type === OpenAI | OpenAIResponses | undefined`）
- **执行链路**：`ImageGenerationService.generate()` 对非 chatbox-ai provider 走 `createModel` → `getModel()` → `model.paint()`，已有实现：`src/shared/models/abstract-ai-sdk.ts:434`、`src/shared/providers/definitions/models/openai-compatible-image.ts`、`gemini-base.ts:88`、`chatboxai.ts:306`。
- **配置门槛**（`getConfiguredImageProviders`）：自定义 provider 需在设置里配置了 `type === 'image'` 的模型；内置 provider 需 apiKey 或 OAuth。

**结论**：需求 1 已满足。若实际使用中某个已配置 provider 未出现在下拉框，多半是该 provider 未配置 `image` 类型模型或鉴权未通过，属配置问题而非功能缺失。

#### 实际测试发现的兼容性问题（落樱云 / gpt-image-2）

用户配置的自定义 provider「落樱云」（`type: openai`，API Host `https://api.crouter.org`）包含 image 模型 `gpt-image-2`（`type: image`，`capabilities: []`），在图片生成页面选中后生成失败（`APP_LOG: Image generation failed: AI_APICallError: Invalid JSON response`）。手动探查根因如下。

**链路**：`custom-openai` → `createOpenAICompatibleImageModel` → `@ai-sdk/openai` `provider.image(modelId)` → `generateImage()`

**`@ai-sdk/openai` v4.0.60 的行为**（`node_modules/@ai-sdk/openai/dist/index.js`）：

1. 请求：对不在默认列表（dall-e-2/3、gpt-image-1 等）的模型，强制发送 `response_format: "b64_json"`（`...!hasDefaultResponseFormat(this.modelId) ? { response_format: "b64_json" } : {}`）。`gpt-image-2` 不在列表，故会带该参数。
2. 响应 schema（`openaiImageResponseSchema`）严格要求 `data[].b64_json` 字段，无 `url` 兜底。

**落樱云 `gpt-image-2` 的实际响应**（手动 curl 验证）：

| 请求 | 返回 |
|---|---|
| 不带 `response_format` | `{created, data:[{url:"data:image/jpeg;base64,..."}]}`（HTTP 200） |
| 带 `response_format:"b64_json"` | 不稳定：成功时 `{data:[{b64_json:"..."}]}`；Free 分组经常 500 `get_channel_failed` |

**失败情形**：
- 情形 A（最常见）：SDK 强制带 `b64_json`，落樱云忽略该参数仍返回 `url` 字段 → schema 校验失败 → `Invalid JSON response`。
- 情形 B：Free 分组渠道不可用 → 500（服务端限流，非客户端问题）。

**兼容方案（待实现）**：给自定义 OpenAI 兼容 provider 的图片模型走一条不依赖 `b64_json` schema 的自定义请求路径——直接 fetch `/v1/images/generations`，响应里同时兼容 `b64_json` 与 `url`（data URL 或 http URL），统一转成 base64 data URL 返回。不修改 ai-sdk，升级安全；兼容落樱云这种"返回 data URL"的非标准实现。
