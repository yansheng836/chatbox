# 项目改造计划

## 目的

准备基于这个项目 https://github.com/chatboxai/chatbox 进行改造，添加一些额外的功能。

为了方便继续合并上游代码，尽量会以独立的方式新增功能，以最少的代码进行改造。

尽量实现 Windows+Android 两端就行了，如果不复杂的话，其他端也同步实现，具体看功能。

## 需求

### 1.新增第三方API生图

目前官方只支持他自己的生图，不支持第三方，需要参考对话模式那样能选到自行配置的生图API。

#### 分析结论（2026-11-02）

经代码核查，**该需求在当前 fork（chatboxai/chatbox CE）中已完整实现，无需改动代码**：

- **左侧导航入口**：`src/renderer/Sidebar.tsx:115` 已有跳转 `/image-creator` 的按钮。
- **图片生成页面**：`src/renderer/routes/image-creator/index.tsx`，输入框下方左侧即模型下拉框 `ImageModelSelect`。
- **下拉框已支持的第三方 provider**（`useImageModelGroups` → `buildImageModelGroups`，见 `packages/chatbox-core/src/application/image-generation/catalog.ts`）：
  - ChatboxAI（官方）
  - OpenAI（非 OAuth 鉴权时）
  - OpenRouter
  - Gemini（内置 + 自定义 Gemini provider）
  - **自定义 OpenAI 兼容 provider**（`catalog.ts:142-150`，匹配 `type === OpenAI | OpenAIResponses | undefined`）
- **执行链路**：`ImageGenerationService.generate()` 对非 chatbox-ai provider 走 `createModel` → `getModel()` → `model.paint()`，已有实现：`src/shared/models/abstract-ai-sdk.ts:434`、`src/shared/providers/definitions/models/openai-compatible-image.ts`、`gemini-base.ts:88`、`chatboxai.ts:306`。
- **配置门槛**（`getConfiguredImageProviders`）：自定义 provider 需在设置里配置了 `type === 'image'` 的模型；内置 provider 需 apiKey 或 OAuth。

**结论**：需求 1 已满足。若实际使用中某个已配置 provider 未出现在下拉框，多半是该 provider 未配置 `image` 类型模型或鉴权未通过，属配置问题而非功能缺失。

#### 实际测试发现的兼容性问题（落樱云 / gpt-image-2）

用户配置的自定义 provider「落樱云」（`type: openai`，API Host `https://api.crouter.org`）包含 image 模型 `gpt-image-2`（`type: image`，`capabilities: []`），在图片生成页面选中后生成失败（`APP_LOG: Image generation failed: AI_APICallError: Invalid JSON response`）。手动探查根因如下。

**链路**：`custom-openai` → `createOpenAICompatibleImageModel` → `@ai-sdk/openai` `provider.image(modelId)` → `generateImage()`

**`@ai-sdk/openai` v4.0.60 的行为**（`node_modules/@ai-sdk/openai/dist/index.js`）：

1. 请求：对不在默认列表（dall-e-2/3、gpt-image-1 等）的模型，强制发送 `response_format: "b64_json"`（`...!hasDefaultResponseFormat(this.modelId) ? { response_format: "b64_json" } : {}`）。`gpt-image-2` 不在列表，故会带该参数。
2. 响应 schema（`openaiImageResponseSchema`）严格要求 `data[].b64_json` 字段，无 `url` 兜底。

**落樱云 `gpt-image-2` 的实际响应**（手动 curl 验证）：

| 请求 | 返回 |
|---|---|
| 不带 `response_format` | `{created, data:[{url:"data:image/jpeg;base64,..."}]}`（HTTP 200） |
| 带 `response_format:"b64_json"` | 不稳定：成功时 `{data:[{b64_json:"..."}]}`；Free 分组经常 500 `get_channel_failed` |

**失败情形**：
- 情形 A（最常见）：SDK 强制带 `b64_json`，落樱云忽略该参数仍返回 `url` 字段 → schema 校验失败 → `Invalid JSON response`。
- 情形 B：Free 分组渠道不可用 → 500（服务端限流，非客户端问题）。

**兼容方案（已实现，2026-11-02）**：给自定义 OpenAI 兼容 provider 的图片模型走一条不依赖 `b64_json` schema 的自定义请求路径——直接 fetch `{apiHost}/images/generations`，响应里同时兼容 `b64_json` 与 `url`（data URL 或 http URL），统一转成 base64 data URL 返回。不修改 ai-sdk，升级安全；兼容落樱云这种"返回 data URL"的非标准实现。

#### 实现内容（2026-11-02）

改动文件：

| 文件 | 改动 |
|---|---|
| `src/shared/providers/definitions/models/openai-compatible-image.ts` | 移除 `createOpenAICompatibleImageModel`（原经 `@ai-sdk/openai` 的 image model）；新增 `generateImageWithOpenAICompatibleAPI`、`detectImageMediaTypeFromBase64`、`convertImageUrlToBase64DataUrl` |
| `src/shared/providers/definitions/models/custom-openai.ts` | 删除 `getImageModel()`；override `paint()`，改用 `generateImageWithOpenAICompatibleAPI` |
| `src/shared/providers/definitions/models/custom-openai-responses.ts` | 同上 |
| `src/shared/providers/definitions/models/openai-compatible-image.test.ts` | 重写：覆盖 `b64_json`、data URL、远程 URL、错误提取、空数据等场景；保留 OpenRouter 测试 |

实现要点：

1. **请求**：POST `{apiHost}/images/generations`，body 为 `{model, prompt, n, size?, images?}`，**不发送 `response_format`**（落樱云等非标准实现不受该参数约束）。
2. **响应兼容**：`data[]` 中优先取 `b64_json`，其次取 `url`；`url` 为 `data:` 时直通，为 http(s) 时下载后转 base64 data URL。
3. **媒体类型探测**：`b64_json` 无媒体类型信息，按 base64 魔数识别 JPEG（`/9j/`，落樱云实际返回）、PNG（`iVBOR`）、GIF（`R0lGOD`）、WebP（`UklGR`），默认 PNG。
4. **错误提示**：非 2xx 时解析响应体，优先取 `error.message`，其次 `message`，否则回退 `Image generation failed with status {status}`。该错误写入 `record.error`，由 `ImageGenerationErrorTips` 展示（无特定 errorCode 时直接显示错误文本）并提供「重试」按钮。
5. **逐张持久化**：`paint()` 按 `num` 逐张请求，每张生成后立即回调，与既有 `ImageGenerationService` 的持久化流程一致（单次请求失败不会丢失已生成的图片）。

**验证**：

- 单测：`pnpm vitest run src/shared/providers/definitions/models/` 共 110 通过、0 失败、6 跳过
- 类型检查：改动文件无 TS 错误（`packages/chatbox-core/src/io/zip.test.ts` 的报错为既有问题，与本次无关）
- Biome 格式化/检查通过
- **真实 API 实测**（落樱云 `gpt-image-2`）：连续 3 次成功，返回 `data:image/jpeg;base64,...`，单次耗时约 15-18 秒；401 错误时正确提取 `Invalid token (request id: ...)`

#### Agnes 图生图兼容（2026-11-02）

用户又配置了 Agnes provider（`type: openai`，API Host `https://api.agnes-ai.cn`），含 image 模型 `agnes-image-2.1-flash` / `agnes-image-2.5-flash`。图生图报错。

**Agnes API 的非标准点**（文档 https://www.agnes-ai.cn/zh-Hans/docs/agnes-image-20-flash + 手动 curl 验证）：

1. `response_format` **不能放请求体顶层**，必须放 `extra_body` 内部。
2. 图生图的参考图片放 `extra_body.image` 数组（支持公网 URL 或 Data URI Base64），**不是** OpenAI 标准的顶层 `images: [{image_url}]`。发错位置时返回 400 `images 不是文生图队列支持的字段`。
3. URL 输出模式下 `data[].b64_json` 为空字符串 `""`（非 null），`data[].url` 为远程 https URL（需下载转 base64）。
4. `size` 文档标为必填，实测可省略；`n` 不支持（每次请求返回 1 张）。

**实现**（`openai-compatible-image.ts`）：按模型名 `agnes-image*`（正则 `/^agnes-image/i`）分支处理：

- 新增 `isAgnesImageModel(modelId)` 与 `buildAgnesImageRequestBody(...)`。
- Agnes 分支 body：`{model, prompt, size?, extra_body: { response_format: "url", image?: [...] }}`，**不发送 `n`、不发送顶层 `images`**。
- 非 Agnes 分支保持原样（落樱云等标准/半标准实现）。
- 响应解析复用既有逻辑：空 `b64_json` 因 `length > 0` 判断被跳过，落到 `url`；远程 URL 由 `convertImageUrlToBase64DataUrl` 下载转 base64。

**验证**：

- 单测：新增 3 个 Agnes 分支测试（图生图 body 结构、文生图不带 image、空 b64_json 跳过），`src/shared/providers/definitions/models/` 共 113 通过、0 失败、6 跳过
- **真实 API 实测**（`agnes-image-2.1-flash`）：文生图成功（PNG，867KB）；图生图成功（PNG，1.0MB），远程 URL 正确下载转 base64
